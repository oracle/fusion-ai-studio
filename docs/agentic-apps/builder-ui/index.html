Using the Builder UI¶

The Agentic Application Builder (Builder UI) is the main workspace for creating, configuring, previewing and publishing Agentic Apps. Every setting is visual and every change auto-saves.

Before you start

The agent teams you plan to use must already exist in AI Agent Studio and must be exposed to Agentic Apps. Otherwise they won't appear in the Builder's agent picker. See Configure Agents.

Step 1 — Create the app¶

  1. In AI Agent Studio, open Applications.
  2. Create a new app and enter its basic details, then click Update.
  3. The Builder landing page opens. You can now:
    • Describe your goal in natural language. The builder suggests an application structure and recommends agents that fit (Oracle-delivered, partner or your own). Accept a suggestion and refine it.
    • Click Start from scratch to open an empty Builder and assemble your own agents.

Intent → assembly → refinement

The natural-language path has three phases. First, describe the business objective (for example, "a workspace that helps executives track major initiatives"). Next, accept the proposed structure and agents. Then refine the layout, names, prompts and extra expertise before you publish.

The Builder toolbar¶

Control Purpose
Undo (↶) Reverse the last change
Redo (↷) Re-apply the last undone change
Run app preview (▶) Run the app in Preview mode with live agent responses
Publish Make the app available to users with the configured security roles
Browse app components Browse Document Templates, Actions, Related Apps, and Workflows; use Create action or Create template in the corresponding section

Step 2 — Configure app settings¶

Open App Settings using Open property panel next to the app title.

See App Settings for the full list of settings, summaries, and links to feature-specific configuration.

Setting Description
Title App display name shown in the header and app catalog. Keep it short and descriptive.
Subtitle Optional static tagline under the title
Dynamic Title and Subtitle Agent Optional. Nominate an agent that returns a personalized subtitle at startup (InitTitle and InitSubtitle)
Security Roles Only users with these roles can open the app
Initially hide actions panel when empty Hide the actions panel at first. Useful for mainly advisory apps; users can still reveal it.
Automatically translate agent responses Use language settings configured in the app's workflows
Page Options Column layout for agent panels: single-column, two-column or asymmetric

Step 3 — (Optional) Assign static agents¶

Two static agent containers sit at the top of the Builder canvas:

Click the Ask Oracle container, then Custom Query Agent Code, and pick an agent team from the searchable list. Every question typed into the Ask Oracle bar is sent to this agent (stored as queryAgent). See Ask Oracle.

Click the Summary container, then Assign Custom Agent. In the editor, write a Summary Prompt, for example:

Provide a 1–2 sentence executive summary highlighting the most critical
items across all domains. Lead with the count of items needing action today.

When to leave these empty

If you don't assign static agents, the Agentic App Orchestrator handles both jobs on its own. It combines the summaries of every agent marked Include in Summary, and it routes Ask Oracle questions to the best-matching panel agent. Assign static agents only when you need a single, consistent voice or behavior the orchestrator doesn't provide.

Step 4 — Add and configure domain agents¶

The center of the Builder shows the page layout, with each agent drawn as a card in a slot. Click a card to open the Agent Editor. Use the canvas controls to add or rearrange slots.

Agent Code Search for and select the agent team bound to this slot. Its description is shown for confirmation and is also used for routing. —
Display Name of Advisor Heading shown on the agent's card —
Include in summary? + Initial Summary Prompt Contribute to the top summary Summary
Include in actions? + Initial Actions Prompt Allow the agent to suggest actionable insights InitActions
Initial Graphics Display Instructions What the agent renders in its card at startup InitDisplay
Override widgets used? Use the widget styles chosen in this app instead of the ones set on the agent —

Example prompts:

Initial Summary Prompt
Summarize the key compliance gaps and any overdue certifications in 1–2 sentences.
Initial Actions Prompt
Suggest an action only when a certification deadline is within 7 days or already
overdue. Keep titles under 10 words and start with a verb. Pass the employee ID
as the payload: ora.Invoke("assignTraining", "<PERSON_ID>").
Initial Graphics Display Instructions
Show the 5 most critical compliance items using the message list widget with
priority badges. Each item: employee name, requirement, days overdue, one-line reason.

Tip

Add domain agents one at a time and check each one in Preview before adding the next. It makes problems much easier to isolate.

Step 5 — Templates and communications¶

Communications that are app-defined need a template, so create the template first.

  1. From the toolbar, click Browse app components › Document Templates › Create template and choose PowerPoint, PDF, Email or Text.
  2. Fill in each section's generation instructions (what to write) and presentation instructions (how to format it).
  3. In the Communications list on the right of the canvas, click Add Communication and fill in:
Field Description
Title Name shown in the communications panel
Description When the communication should be suggested. Agents use this to judge relevance.
Applicable Agents Which agents may suggest it
Template The template created in step 1
Action Text (Email/Text) Button label, e.g. "Send Email", "Alert Team"
Target Agent (Email/Text, optional) Agent that delivers the message. Email uses the configured mail client.
  1. Tick Include in Communications? on each agent that should suggest it.

Full details: Communications.

Step 6 — Actions¶

  1. From the toolbar, click Browse app components › Actions › Create action (or open Browse app components › Actions).
  2. Fill in Code (sent to the agent with InvokeAction), Display Name and an optional Description.
  3. Add steps in order: Keep Action Available in UI, Navigate to App, Send Agent Command, Refresh Agents, Switch App Context.

Full details: Actions.

Step 7 — Preview¶

Click Run app preview (▶) to run the app against live agents. Test:

  • Every initialization hint: subtitle, summary, displays, actions, communications
  • Ask Oracle in the Summary View and in each Section Focus View
  • Every action, end to end, including refreshes and navigation
  • Every communication: suggest → fill → review → send
  • Latency: every path well under the 60-second limit

Step 8 — Publish¶

Click Publish to release the app to users who have the configured Security Roles. You can keep editing after publishing; changes go live only when you re-publish.

Checklist: your first app¶

  1. Create the app with a clear title and subtitle.
  2. (Optional) Assign the Ask Oracle and Summary static agents.
  3. Add domain agents one by one, with Summary, Actions and Display prompts for each, and preview each one.
  4. Create templates, then communications, and assign applicable agents.
  5. Build actions in the Actions Editor and test each flow.
  6. Preview thoroughly and iterate on prompts.
  7. Publish, monitor usage and re-publish as you improve the app.

Builder, action editor, and workflow versions¶

The app builder configures the app shell, panels, app-level agents, communications, Ask Oracle, and autonomy. Open an item under Browse app components › Actions to edit its ordered onInvoke steps, or under Browse app components › Document Templates to edit a reusable artifact definition. The app-level Dynamic Title and Subtitle Agent setting is separate from the Query and Summary agents.

Multiple top-level panels sharing one agent¶

Several top-level panels can use the same workflow agent while showing different startup displays. Reuse an agent when the panels need the same data source, tools, or domain skills, then configure each panel's display separately.

  1. Select the top-level panel in Builder view and choose its Agent code.
  2. Set Initial graphics display instructions to describe what that panel should show when the app opens.
  3. Set Override widgets used to the widget types that match those instructions and are enabled on the workflow node.
  4. Read the panel's Display discriminator when the workflow needs to distinguish it from other panels using the same agent.
  5. Repeat for each panel backed by the shared agent.

Panel-specific startup instructions take precedence over the agent's shared/default startup display. The shared default is a fallback. To change one panel's graphics, edit that panel's instructions rather than changing the shared default for every panel.

For example, two panels can share a supplier workflow:

Panel Initial graphics display instructions Override widgets used
Delivery Show monthly on-time delivery rates as a line chart, highlighting recent declines. Chart
Contracts List contracts expiring within 30 days, with supplier, expiry date, and owner columns. Multi Record

Each panel sends its own InitDisplay request. In the workflow, route with $context.$app.$OraAppDisplayDiscriminator when the two displays need different handling. Match the actual values shown in Builder; the following uses illustrative discriminator values:

If OraMessageHint is InitDisplay:
  If OraAppDisplayDiscriminator is "deliveryPanel":
    produce the delivery chart
  Else if OraAppDisplayDiscriminator is "contractsPanel":
    produce the expiring-contract table
  Else:
    produce the shared default display

Use $context.$app.$OraPanelName for additional focused panels requested with AdditionalContent. Top-level startup panels use InitDisplay and $OraAppDisplayDiscriminator.

Preview each panel to check its instructions, widget override, and workflow routing together. Confirm that changing one panel's startup instructions produces the intended display in that panel.

Develop with draft workflows¶

Use draft workflow while developing lets a top-level panel call its draft workflow in developer mode. A Using draft badge identifies the panel. End-user runtime continues to use published workflows.

Publishing the app is blocked if a panel is set to use draft while developing and its workflow has no published version. If a published version exists, publishing may warn that the draft workflow also needs to be published. Verify the published workflow contains the changes you intend users to receive.

See Autonomous Outcomes for Additional Agents and capability version selection.
