Multi-Agent Architecture¶

Agentic Apps are built from composable, specialized agent teams, not from one generalist agent. Think of the app as an advisory board of experts rather than a single consultant.

Why multi-agent beats monolithic¶

Early conversational apps used one agent with one large prompt because the interface was a single chat stream. That approach overloads the context window, keeps domain knowledge shallow, and turns every change into a regression risk.

Benefit Explanation
Focused context Each agent sees only data from its own domain. Less noise means sharper analysis and fewer hallucinations caused by mixed-up context.
Domain-specific reasoning Prompts, tools and reasoning are tuned per domain. A compliance agent knows audit frameworks; a finance agent knows variance analysis.
Scalability without fragility New capability means a new agent. Existing agents are untouched.

How requests are routed¶

Requests from the app go to the Agentic App Orchestrator, which sends them to the right specialist(s):

Request type Routed to
Initialization (Summary, InitDisplay, InitActions, InitCommunications) Participating agents and panels according to their configured roles and inclusion settings
InitTitle The nominated Dynamic Title and Subtitle Agent only
InitSubtitle The nominated Dynamic Title and Subtitle Agent only
Ask Oracle Query in Summary View The dedicated Query agent, or the relevant agents chosen by the orchestrator from agent descriptions
Ask Oracle Query in Section Focus Only the agents powering that section
InvokeAction Agent follow-up from an action step; app-defined actions first run their configured chain
FillParameters / SendCommunication The designated communications / target agent
AdditionalContent The agent that owns the panel 
flowchart TB
    UI[Agentic App UI] --> O{Agentic App<br/>Orchestrator}
    O -->|init: fan-out| A1[Compliance agent]
    O -->|init: fan-out| A2[Learning agent]
    O -->|init: fan-out| A3[Passport agent]
    O -->|query: by description| A1
    O -->|InvokeAction: owner| A2
    O -->|comms| A4[Communications agent]
    A1 & A2 & A3 & A4 --> R[Assembled response:<br/>displays + actions + comms]
    R --> UI

The user sees one coherent app, not a set of separate agents.

Descriptions drive routing

The orchestrator matches user intent against each agent team's description. A vague description ("handles requests") makes routing unpredictable. A precise one ("analyzes spend variance against budget and surfaces anomalies for approver review") gives the orchestrator what it needs to route correctly.

Agent team type: workflow vs. supervisor¶

Each specialist agent is an agent team of one of two types:

A structured graph of nodes (routing/switch, code, LLM and agent nodes) that handles each request deterministically.

  • Structured routing. The workflow branches on $OraMessageHint, so Summary and InitDisplay follow different paths.
  • A prompt per request type. Each hint gets its own handler and prompt.
  • Predictable latency. A fixed graph means a known number of LLM calls.

A single-worker supervisor team that decides at runtime which tools to call, how many LLM passes to make and when to stop.

  • Maximum flexibility.
  • Latency and output are less predictable, so it needs careful prompting to stay within the time limit.
  • Use it only when a workflow can't express the logic, for example dynamic multi-turn collaboration.

Architecture decision guide¶

Decision Recommendation
Agent team type Workflow first; supervisor only as a fallback
Single vs. multi-agent Use specialists for distinct domains; one workflow can power several panels
Team granularity Small topic areas; combine agents at the app level
Context passing Pass $context.$system.$inputMessage (and $chatHistory) explicitly. It is never automatic.
Terminal workflow paths Prefer Agent/LLM endings for generated prose; strict JSON paths can use deterministic Code/Return nodes
Communication type Template-based for PowerPoint/PDF; agent-generated for ad-hoc email/text
Action invocation ora.Invoke() for defined action workflows; ora.Agent() for ad-hoc agent commands
Widget selection Match the widget to the data story (guide)
Drill-down navigation ora.App.launch() or a Navigate to App action step
Response time 60-second budget from the original draft; verify for your release. Minimize LLM/agent nodes per path and test latency in Preview.

Worked example: HCM Compliance Workspace¶

An HR operations team needs to monitor regulatory compliance, training completion and work authorization for a global workforce.

Agent Role Typical widgets
Compliance agent Audit requirements, regulatory deadlines, policy violations cardWidget (critical alerts), messageListWidget (prioritized items)
Learning agent Training completion, overdue certifications, skill gaps chartWidget (completion trend), multiRecordWidget (training records)
Passport agent Work permit expiry, visa status, document verification cardWidget (urgent expiry), changeListWidget (status changes)
Communications agent Shared, reusable agent that delivers email and chat notifications for all the others —
Summary agent (static, optional) Rolls up each specialist's top insight into 1–2 sentences —
Ask Oracle agent (static, optional) Routes questions to the right specialist —

When the HR Operations Manager opens the app, they see a summary ("7 items need review: 2 critical compliance gaps, 3 overdue trainings, 2 expiring work permits"), four specialist sections, a prioritized actions panel and suggested follow-up emails. Asking "Which teams have the most overdue items?" inside the Compliance section gets an answer from the compliance specialist, not a generalist.
