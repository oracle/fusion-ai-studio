Core Concepts & Lifecycle¶

This page connects the theory to the configuration surface. It covers what defines an app, the framework components you assemble, the visual tools you use, and the runtime lifecycle.

App configuration structure¶

Every Agentic App is defined by an application configuration (appConfig). The visual tools configure it; pro-code tooling can also manage app artifacts. Publishing makes the configured app available to its intended users. Knowing its shape tells you what you're configuring.

Property Description Set in
title Display name in the header bar and app catalog App Settings
subTitle Optional text below the title. Static, or generated by an agent App Settings
subtitleAgentCode Optional. The agent that generates the subtitle at startup (InitTitle and InitSubtitle) App Settings › Dynamic Title and Subtitle Agent
pageConfig Column layout of agent panels Page Options
agents The domain agents, each assigned to a layout slot Builder canvas
queryAgent Optional dedicated agent for Ask Oracle Ask Oracle static slot
summary Optional dedicated summary agent and its Summary Prompt Summary static slot
communications Communications that agents can suggest Communications panel
actions Reusable multi-step action workflows Actions Editor
templates Email, Text, PowerPoint and PDF templates Template Editor
initiallyHideActions Hide the actions panel when empty (users can reveal it) App Settings

The four framework components¶

Component Layer What it is
Agents Intelligence Agent teams built in AI Agent Studio. The only component that reasons. Everything else renders, routes or delivers what agents produce.
Widgets Visualization Eleven display types rendered from agent JSON metadata in Agentic Apps. See Widgets.
Communications Outreach Outbound email, text, PowerPoint and PDF. Either app-defined (template) or agent-generated. See Communications.
Actions Execution Reusable step chains (keep available, navigate, send agent command, refresh agents, switch context). See Actions.

Before an agent can be used in an app, it must be exposed to Agentic Apps in AI Agent Studio, with its allowed widgets, actions and communications enabled. See Configure Agents.

The visual configuration tools¶

Tool Where Purpose
AI Agent Studio (agent team editor) Agents area of the studio Build each agent's workflow, prompts, tools and App Experience settings
Builder UI Apps area of the studio App settings, layout, static agents, domain agents and their prompts, communications, preview and publish
Actions Editor Builder toolbar › Browse app components Build reusable multi-step actions
Template Editor Builder toolbar › Browse app components Design Email, Text, PowerPoint and PDF templates using generation and presentation instructions

Two-tab workflow

Keep AI Agent Studio open in one browser tab and the Agentic App Builder in another. Apps auto-save, so you can change an agent workflow in one tab and immediately re-run Preview in the other.

The app lifecycle¶

The framework calls agents with a message hint ($context.$app.$OraMessageHint) that says what it needs. Agent workflows branch on that value. See the full Message Hints reference.

Phase 1 — Parallel initialization¶

The original startup model includes five initialization hints that can run in parallel, according to the configured agents and features:

Hint Sent to Produces
InitTitle The Dynamic Title and Subtitle Agent Personalized title, e.g. "Shortage Workspace - Vision Operations"
InitSubtitle The Dynamic Title and Subtitle Agent Personalized tagline, e.g. "Good morning, Meg. 3 items need review."
Summary Agents with Include in summary? (or the Summary agent) 1–2 sentence executive overview
InitDisplay Every domain agent Startup widgets, driven by the display prompt
InitActions Agents with Include in actions? Priority actionable insights
InitCommunications Agents with Include in Communications? Suggested outreach

The communication lifecycle¶

Every communication goes through five stages. See Communications › Lifecycle.

  1. Suggest — an agent recommends it (at InitCommunications or in a response).
  2. Prefill — the agent fills the parameters it already knows.
  3. Fill parameters — when the user selects it, FillParameters asks an agent to complete any remaining fields.
  4. User review — the user edits anything, or cancels. The human stays in control.
  5. Send — the template engine renders the output, and SendCommunication goes to the delivering agent.

From configuration to experience¶

flowchart LR
    subgraph Build time
      AS[AI Agent Studio<br/>workflows, prompts, App Experience section]
      BU[Builder UI<br/>shell, layout, agents, comms]
      AE[Actions Editor]
      TE[Template Editor]
    end
    AS & BU & AE & TE -->|Publish| CFG[(appConfig)]
    CFG --> RT[Runtime framework]
    RT -->|message hints| AG[Agent workflows]
    AG -->|displays · actions · comms| RT
    RT --> USR[Unified app experience]

At build time, the four tools define the app. Publish generates the configuration. At runtime, the framework sends hints to agents, the agents return structured output, and the framework renders one unified experience.

Additional app-aware stages¶

Additional requests support context selection (InitContextSuggestions, QueryContextSuggestions), dynamic starter queries (InitSampleQueries), and Ask Oracle lookups (QueryFilterValues). Autonomous capability invocation uses a distinct InvokeCapability route. These are feature-specific requests, not five extra calls every app must make on startup.

InitDisplay can return actions and communication suggestions alongside widgets. Separate startup action and communication stages remain useful when configured. See the expanded Message Hints and Context Variables references.
