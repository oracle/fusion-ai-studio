Configure Agents for Agentic Apps¶

An agent team takes part in an Agentic App through configuration on two surfaces:

Surface Scope Decides
AI Agent Studio (agent team editor) Global. Changes affect every app that uses the team. What the agent is capable of producing: exposure, widgets, actions, communications, house-style instructions
Agentic App Builder (Agent Editor) Local. Applies to one slot in one app. What the agent contributes to this app: summary, actions and display prompts, communications, panels

The same team can be reused in many apps, and each app can use a different subset of its capabilities.

Order matters

Always configure AI Agent Studio first. The App Builder can only use capabilities that were enabled in the agent team. Skipping this step causes most "why isn't this working?" problems.

Part 1 — Build the workflow to respond to message hints¶

Every call from the app carries a message hint in $context.$app.$OraMessageHint. The standard pattern is one workflow per agent with a Switch node that branches on the hint and sends each value to its own handler node.

flowchart LR
    IN([Request]) --> SW{Switch on<br/>$OraMessageHint}
    SW -->|Summary| N1[LLM: summary]
    SW -->|InitDisplay| N2[Agent: initial display]
    SW -->|InitActions| N3[LLM: actions]
    SW -->|InitCommunications| N4[LLM: comms]
    SW -->|Query| N5[Agent: query<br/><small>+ $chatHistory</small>]
    SW -->|InvokeAction| N6[Agent: execute action<br/><small>uses $OraAction</small>]
    SW -->|AdditionalContent| N7[LLM: panel content<br/><small>by $OraPanelName</small>]

Use Workflow as the team type. It gives you structured input, a prompt per request type, and predictable latency within the 60-second budget. See Architecture.

Context is not passed automatically

Internal nodes do not automatically receive the user's message or chat history. Pass $context.$system.$inputMessage (and $context.$system.$chatHistory for queries) to every node that needs them. A missing variable is the most common reason an agent "ignores what the user said".

End terminal paths on Agent or LLM nodes

For generated prose and displays, prefer an Agent or LLM terminal node where its response behavior is needed. Use deterministic Code/Return endings for strict JSON contracts such as starter queries when appropriate.

Part 2 — Expose the agent and set up the App Experience section¶

Step 1: Turn on Expose to Agentic Apps¶

At the bottom of the agent team's Details panel, switch on Expose to Agentic Apps. This is the master switch.

  • On: the team appears in the App Builder's agent picker, and an App Experience section is added to every Agent and LLM node in the workflow.
  • Off: the team won't appear properly in the App Builder, whatever else you configure.

Step 2: Configure the App Experience section on each node¶

Open each Agent/LLM node that produces app content, then go to the App Experience section:

Setting Effect
Enable Actions for the widgets Lets the node emit <oraInsight> blocks (actions). If this is off, no prompt can produce actions.
Enable Communications for the widgets Lets the node emit <oraComms> blocks (suggested emails/messages)
Select the widgets you want to use Which of the eleven widget types the node may render. Select at least one to turn on information displays.
Instructions General formatting rules and guidance on when to use each selected widget. This is the agent's "house style" in every app. Put app-specific instructions in the App Builder, not here.

Step 3: Write a clear team description¶

The orchestrator uses the team description to filter and route requests, especially Ask Oracle queries. Describe capabilities in specific verbs and nouns:

Weak Strong
"Handles finance requests." "Analyzes spend variance against budget by cost center and quarter, flags anomalies above threshold, and recommends approver actions."

Part 3 — Configure the agent in the App Builder¶

In the App Builder, click the agent card to open the Agent Editor: the per-app controls for this agent.

Agent Code¶

Search for and select the agent team. Only teams with Expose to Agentic Apps turned on are listed. Check the description shown under the field to confirm you picked the right team.

Include in Summary¶

Shows an Initial Summary Prompt, which is sent with the Summary hint.

Summarize the key spend variance metrics and any anomalies detected in 1–2 sentences.

Include in Actions¶

Shows an Initial Actions Prompt, which is sent with InitActions. State the conditions that justify an action and how to word it.

Suggest actions when budget variance exceeds 10% or a milestone is at risk of slipping. Keep titles short and start with a verb.

Upstream dependency

Include in actions? only works if Enable Actions for the widgets is on in the App Experience section. If it is off, ticking the box here does nothing. This is the most common configuration mistake across the two products.

Initial Graphics Display Instructions¶

The prompt behind the agent's startup display (InitDisplay). Name the widget and limit the size of the output.

Show the top 5 items by impact score using the message list widget. Each row: item name, impact value, one-line reason.

Include in Communications¶

Lets the agent suggest the app's communications (InitCommunications). For agent-generated communications, Enable Communications for the widgets must also be on in AI Agent Studio.

Active¶

The Active property, located after Include in Communications?, controls whether the App panel is available to the signed-in user. Configure an expression that checks whether the user has the required role or permission. When the condition evaluates to true, the panel is available; when it evaluates to false, the panel is unavailable.

For example, make an approval panel available only to users with the approver role, or a restricted reporting panel available only to users with the required reporting permission. Use the role or permission identifier configured in your environment.

This setting applies to the individual panel. App-level access is configured separately through Security Roles. Test the panel with users who satisfy the condition and users who do not.

Panels¶

Panels are extra content sections that load on demand when the user focuses on this agent's section.

  1. Click + Add Panel at the bottom of the Agent Editor.
  2. Name: internal identifier in snake_case, e.g. variance_details
  3. Heading: title shown to users
  4. Prompt: what the panel should contain

At runtime the agent receives the AdditionalContent hint, with the panel's name in $context.$app.$OraPanelName. Branch on that value to pick the right handler.

Dynamic Title and Subtitle Agent¶

The Dynamic Title and Subtitle Agent field is set at app level in App Settings, not per agent. The nominated agent receives InitTitle and InitSubtitle at startup and returns a title and short tagline.

Layered prompts¶

Layer Where Contains
Agent/LLM node prompts AI Agent Studio Domain reasoning, tool use, data access
Instructions App Experience section Formatting rules and widget usage shared by all apps
Summary / Actions / Display / Panel prompts App Builder Agent Editor What this agent should contribute to this specific app

Don't repeat the same instruction across layers. Duplicates drift apart and conflict.

Stage-specific prompt examples¶

Route to a separate handler before applying these instructions. Include the app-supplied input explicitly so the node receives the panel's current instructions.

InitDisplay handler prompt
App context: {{ $context.$app.$OraAppContext }}
Startup panel: {{ $context.$app.$OraAppDisplayDiscriminator }}
Current user: {{ $context.$app.$OraUserContext.fullName }}
App-supplied input: {{ $context.$system.$inputMessage }}

Retrieve succession coverage for the current manager's direct reports.
Return an oraInfoDisplay using the messageListWidget. Highlight missing plans
and gaps in ready-now coverage. Use only retrieved records.
Add an action or communication suggestion only when a useful follow-up exists.

InitDisplay can return actions and communications alongside displays when the node's App Experience settings allow them. Keep dedicated InitActions and InitCommunications handlers for requests using those hints; each handler should return the output for its own stage.

Query handler prompt
Current question: {{ $context.$system.$inputMessage }}
Conversation: {{ $context.$system.$chatHistory }}
App context: {{ $context.$app.$OraAppContext }}
Additional query context: {{ $context.$app.$OraAskOracleContext }}
Attachments: {{ $context.$app.$OraAttachments }}

Answer the question using the available data. Resolve follow-up references
from the conversation. Include displays, actions, or communications when useful.

Only pass attachments to a handler equipped to read them. For action and form handlers, inspect the received input as described in Actions and Record widget.

End-to-end configuration checklist¶

In AI Agent Studio

  • Team type is Workflow, and the description lists the team's capabilities clearly
  • Expose to Agentic Apps is on, and App Experience sections appear on the nodes
  • Each content-producing node has Enable Actions, Enable Communications and Select the widgets you want to use set as needed
  • The Instructions field holds general formatting and widget guidance
  • A Switch on $OraMessageHint has a handler for each hint the app will send
  • $inputMessage and $chatHistory are passed explicitly where needed
  • Terminal nodes match their output contracts; strict JSON branches return JSON only

In the App Builder

  • The agent is placed in the right layout slot, with Agent Code selected
  • Include in summary? and its prompt (if applicable)
  • Include in actions? and its prompt, with specific triggers
  • Initial Graphics Display Instructions name the widget and limit the output
  • Include in Communications? (if applicable)
  • Panels added for any extra content
  • Dynamic Title and Subtitle Agent set (if this agent supplies the subtitle)
  • Preview: the section fills at startup, actions appear, and clicks reach InvokeAction

See Troubleshooting for symptom-to-cause tables.

Shared startup panels and deterministic outputs¶

A workflow reused by several top-level panels receives a separate InitDisplay request for each panel. Match $context.$app.$OraAppDisplayDiscriminator to the panel value shown in Builder, and keep each panel's graphics instructions and widget override aligned. Additional focus panels continue to use AdditionalContent and $OraPanelName.

See Multiple top-level panels sharing one agent for per-panel configuration, startup instruction precedence, and a routing example.

Use Agent/LLM terminal nodes for generated displays and prose when their response behavior is needed. A deterministic Code or Return branch is appropriate for strict JSON such as InitSampleQueries; do not force structured lookup output through an LLM merely to follow a general terminal-node recommendation.

For autonomous operations, declare workflow capabilities and implement their InvokeCapability or direct-trigger routes as described in Autonomous Outcomes.
