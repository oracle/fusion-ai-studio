# Explicit Artifact Save With Dependencies

Read this reference completely when the user explicitly asks to save a **plugin, application, or workflow with its dependencies** (or equivalent). The model coordinates existing CLI commands; there is no cascading save command. Use this same procedure recursively, irrespective of the starting artifact. Ordinary saves remain single-artifact operations, including any managed skill synchronization already owned by that save.

A save-only request authorizes neither source repair nor semantic review, test generation/execution, publication, credential provisioning, or deployment of external resources. A read-only `testImpact` returned by a save is not a request to run tests. Creation/material-edit lifecycle rules still apply when that work was requested, but do not enter them merely to persist existing sources.

## Inventory And Local Identity

1. Resolve the requested root using `artifact-conventions.md`. Support legacy `src`, packages under `app-pkg`, or packages directly under the workspace root. Read package markers and resolve existing file paths; do not assume legacy extensions. Package apps use `.apps`, deeplinks `.deeplink`, and approvals `.approvalProcess`. Follow actual references across local modules/packages. If the root or a dependency identity is ambiguous, ask instead of choosing the first file. No new artifact creation or layout migration is needed.
2. Read actual structured references in the root, then recursively inspect each locally available dependency using the matrix below. Listing/validation commands are starting inventories, **not proof of the complete graph**. Inspect all source branches, not just an observed execution path. Load existing artifact references only for types encountered; do not load test-authoring or unrelated authoring guidance.
3. Establish **parent artifact and node/configuration location → exact referenced identity → local file with that internal identity → selected save command**. Identity is usually a code; use the documented equivalent for approvals/connectors. Filenames, display names, descriptions, similar names, source proximity, and examples do not establish dependency membership. Read internal identity before selecting the file. Do not substitute an original for a copy, strip suffixes, or rewrite references. References to both original and copy select both.
4. Retain every parent explanation but inspect and save each unique artifact type/identity once. Two local files claiming the same identity are an ambiguity, not permission to pick one. Reuse this inventory for the whole request; recheck affected entries when sources or scope change. Do not create a persistent dependency manifest or add source/test/report metadata. Scratch and prior reports are never required inputs.
5. Account for each reference: included local source, explicit exclusion, missing locally, invalid/ambiguous identity, dynamic/unresolved reference, or unsupported operation. Missing local dependencies are **skips, not errors**: leave server copies untouched, do not download them merely to save them back, and do not claim their descendants were inspected. Malformed files and read/access failures are real failures, not missing-local skips. Do not guess runtime values to resolve a dynamic reference.
6. Validate included sources with existing validators before saving. Validation does not authorize fixing sources. Follow the dependency graph for save order; distinguish an already inspected shared child from a cycle through the current ancestry. Report cycles and block affected branches rather than inventing an order.

## Reference Matrix

Use the actual source schema and artifact-specific command help. A field containing an arbitrary code, URL, prompt mention, or runtime record identifier is not automatically an artifact dependency.

| Source type | References and owned content |
| --- | --- |
| Plugin | Linked `applications`, direct `additionalAutonomousAgents[].workflowCode`, and structured skill workflow associations. Recursively inspect local linked apps and workflows. Capability tokens can explain a reference but are not a substitute for resolving its owner. |
| Application | Inspect `agents[].agent`, panel/additional-panel agent references, `queryAgent`, title/subtitle agent fields, `summary.agentCode`, `appContextView.agentCode`, `dynamicStarterQueries.agentCode`, `queryValueFilters[].workflowCode`, additional autonomous agents, and structured action/communication/custom-channel workflow references. Resolve app-local agent keys through `agents` before choosing a workflow. An app agent usually denotes a workflow, not a standalone `.agent`. For legacy capability owner fields, use the documented existing mapping; do not author new app-level capabilities. Include explicit skill security workflow references. |
| Workflow | Inspect all pipeline nodes, nested loops/branches/parallel containers, and referenceable blocks. Follow child `WORKFLOW` references, `BO_FUNCTION` BOs, tool references, reusable `AGENT` references, private-agent tools/topics, `MULTI_AGENT` topics, `POLICY` codes, `HUMAN` approval-process references, and reusable `CODE` function-template references. For `DOCUMENT_PROCESSOR`, distinguish the BO path from LLM extraction's document-schema template. Typed, static AI Guidance references may identify BOs, apps, or plugins. Signal nodes may identify a signal and explicit subscriber workflows; do not fetch arbitrary subscribers. |
| Agent | Follow normalized `specification.tools` and `specification.topics` code arrays. Legacy mapping arrays are compatibility inputs only. A private agent embedded in a workflow is not a separate file to create/save, but its referenced tools/topics are dependencies. |
| Tool | For BO/deeplink tools, resolve `specification.baseObjectCode` according to the tool type. For connector tools, resolve the documented connector ID/reference key against local connector instances, not similar display names. Retain owned retrieval documents, attachments, and delivery options through the existing tool save; do not invent separate artifact saves or uploads. |
| BO / deeplink / topic | Save through their existing commands. BO functions, deeplink properties and topic instructions remain embedded; do not invent reusable-function or child-artifact files for them. |
| Policy | Follow an explicit policy-template reference and `specification.context.workflowContext` where present. Embedded policy functions are not standalone reusable-function artifacts. |
| Policy template / document schema / reusable function | Preserve normalized owned prompt/schema/function content. Do not infer artifact dependencies by matching words in prompts or executable code. Referenced test cases or sample documents do not authorize executing tests or uploading documents. |
| Approval process | Identity is `moduleIdentifier`; preserve its owned process configuration. Email accounts, business records and credentials are external prerequisites, not artifacts to create. |
| Connector instance | Resolve its exact connector-definition binding against local files. Save instance configuration only; do not provision credentials, sync external content, or publish connectors. |
| Connector definition | Existing save updates an existing server-backed definition with its confirmed ID. Creating a definition through server generation is a separate operation, not an automatic dependency-save fallback. |
| Signal | Inventory referenced `.signal` files, but the CLI exposes fetch, not signal save. Report the unsupported operation; do not call a hidden API or claim the signal was saved. |
| Managed skills | Owned local skill folders follow the existing app/plugin parent save, once. Keep managed V2 synchronization and explicit legacy CI-package handling distinct. Do not upload the same package separately as a dependency or change unrelated packages. |

Model configurations, security-role assignments, external URLs, storage resources, PL/SQL deployment, credentials, and runtime business records are prerequisites rather than new artifact saves. Tests, reports, fixtures and scratch files are not save dependencies. Unknown typed references must be reported, not silently ignored or guessed.

## Save Procedure

Save dependencies before consumers according to the actual graph, not a fixed artifact-type list. An explicit user skip or missing-local skip leaves the server artifact unchanged and allows consumers to proceed against existing server state; this does not prove runtime compatibility. A validation, authorization, backend, unresolved-identity, or unsupported-save failure blocks consuming parents, not unrelated branches. Unsupported operations may be explicitly skipped by the user, but are not silent successful completion.

Reuse each artifact's existing save command and its validation, conflict handling, owned-resource writes and normalization. Dependency coordination is not a new save implementation or a universal version-protection policy. Preserve protections already available for an artifact, but do not invent a stricter prerequisite for another artifact whose ordinary save lacks it.

Save supported publication-based artifacts as `DRAFT`: applications, Ask Oracle plugins, workflows, functions, policies, and document schemas. Publish these artifacts only through CI/CD deployment. The CLI rejects function, policy, and document-schema publication commands. Business Objects, Deep Links, and Policy Templates have no publication status; do not add one.

Fetched supported artifacts are editable local copies. Local `seededFlag: false` does not grant permission to overwrite seeded server content. For artifacts with a draft/published lifecycle, save resolves the actual server draft or permitted customization first. Preserve workflow version confirmation and every existing remote-save guard. Do not retry a rejected save with `--force` to bypass customization restrictions.

For the supported normalization artifacts, code identifies the artifact on the target server; local database IDs do not select a different artifact or replace server primary keys. An existing eligible record is updated using its server ID; an absent ordinary artifact is created with a server-assigned ID. A file containing A's ID and existing code B saves B, subject to B's permissions and conflict checks. Unused code C creates C and leaves A unchanged. Neither case renames A. Save retains the confirmed server identity locally. Customizations still require a resolvable, permitted server parent; a foreign parent ID is not permission to create or reparent a customization.

Tools, topics, and reusable agents retain their native status metadata when fetched. Save updates the existing record regardless of status; never create another record or version merely because it is PUBLISHED. Tool saves use the native PUBLISHED value. New agents use PUBLISHED; new topics and instructions use DRAFT. Agent, topic, and instruction edits preserve the existing server status. These are ordinary saves, not separate publication operations. Ambiguous identities must be resolved before saving.

Signals, approval processes, connector definitions, and connector instances are excluded from this normalization contract. Their existing command behavior remains unchanged; do not describe them as draft-only or auto-save a connector binding while saving a CONNECTOR tool.

Document Tool saves follow the UI's document lifecycle. A successful document or attachment change in `READY_TO_PUBLISH` or `READY_TO_DELETE` starts document processing once; an unchanged document in either state does not. DRAFT document metadata edits do not start processing. Supported document status changes, including returning a document to DRAFT, use the shared Tool save behavior. This document processing is part of Tool Save; lifecycle artifact publication still goes through CI/CD.

- Workflow: retain `do-save-workflow` safeguards. For a newer remote DRAFT, ask overwrite or skip. An approved overwrite uses `--overwrite-remote-draft --expected-remote-version <reviewed-version>`.
- Application, plugin and BO: retain the established dependency-save protection using `do-save-app`, `do-save-ask-oracle-plugin`, and `do-save-bo` with `--guard-remote`. Each command protects and saves only that selected artifact, not its dependencies.
- Agent, topic, tool, deeplink, policy, policy template, document schema, reusable function, approval process and connector: use the existing matching `do-save-* --file <resolved-file>` command without adding `--guard-remote`. Consult its help and type-specific reference. Retain normal writes to owned content and associated configuration; do not suppress them or repeat them through separate dependency commands. Do not reject a supported ordinary save merely because it lacks the above guard. Where the existing save lacks stale-version protection, dependency saving inherits that behavior rather than promising stronger protection.
- Preserve existing conflict decisions for these ordinary saves. For example, an existing approval process requires its documented confirmation before `--allow-conflict-update`; ETag failures or overwrite/force options follow the corresponding command's existing rules. Do not add override flags automatically to make the dependency operation complete.
- `REMOTE_SAVE_CONFIRMATION_REQUIRED`: show the exact artifact and reason, then ask overwrite or skip. A save-with-dependencies request does not itself approve conflicting replacement. Comparable versions, matching revision tokens, and canonical content are different evidence; do not call content differences a higher version when no comparable version exists.
- After approval of an application, plugin or BO guarded-save conflict, repeat that save using `--overwrite-remote-draft --expected-remote-id <returned-id> --expected-remote-etag <returned-etag>`, plus `--expected-remote-version <returned-version>` for an app when reported. Use the exact reviewed evidence. A changed state or HTTP 412 requires a new decision. Never drop an established guard, silently refresh its evidence, or replay an old approval against a newer state.
- Mutate serially. Do not repeat successful shared-child saves. Source normalization alone must not restart discovery or trigger testing. Reconcile actual reference changes if they occur.
- These saves are not an atomic transaction. Do not roll back earlier successes automatically. A connection failure or partial-write warning requires supported read-only reconciliation before another write, not an automatic retry. A remote-save success with local-refresh failure must be reported separately; do not repeat the remote write to repair the file.

Use existing serializers and canonical readback. Preserve identities, paths and file formats. Guarded app normalization updates confirmed metadata only in fields already present; do not introduce `id`, `version`, or dependency bookkeeping. Do not overwrite a concurrently edited local file. Server reads inside save guards are allowed; they are not permission to fetch missing source trees into the workspace.

An operation unsupported by the corresponding ordinary save remains unsupported here. For example, there is no signal save command, connector definition generation is not a save fallback, and tool seed-data restrictions still apply. Report the actual limitation rather than manufacturing a save or claiming success.

## One Consolidated Summary

Reconcile command results with the inventory. Show artifact type, code/equivalent identity, outcome, confirmed resulting server version where applicable, and a concise reason/parent reference. Include shared parent explanations when useful. Account for created, updated, confirmed unchanged, excluded, missing-local skips, user-skipped conflicts, failures, unsupported operations, and blocked parents. Do not label an ETag as a version or use a local version as proof of the resulting server version. Do not claim complete success after partial failure. Save success alone does not prove runtime behavior.

## Examples

- **Workflow root:** `WF1 → AGENT1 → TOOL1 → BO1`, with `AGENT1 → TOPIC1`. Save BO1, TOOL1, TOPIC1, AGENT1, then WF1. Reusable-agent children use the same procedure as direct workflow children.
- **App root:** APP1 references WF1 and WF2; both use BO1. Inspect/save BO1 once, then each workflow, then APP1. Starting from WF1 alone uses the identical subtree procedure.
- **Plugin root:** PLUGIN1 references APP1 and WF2 directly. Reuse the same APP1/WF2 inventory; save the plugin last. Do not save WF2 twice.
- **Partially local:** Five BOs are referenced, but only two exist locally. Save those two; report three missing-local skips and uninspected descendants. Do not fetch the other three.
- **Original and copy:** One nested node references BO1 and another references BO1_COPY. Both are included. If only BO1_COPY is referenced, do not include BO1 merely because its name is similar.
- **Conflict:** The user skips a newer server WF2. Leave it unchanged; continue eligible saves and state that APP1 still references the server's WF2. If WF2 instead fails validation/save, block APP1 while completing independent branches.
- **Cycle or unsupported reference:** Explain the exact cycle/signal/save limitation. Do not remove references or manufacture a save operation to claim completion.
