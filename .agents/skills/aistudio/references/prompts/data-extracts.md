# Data Extracts

Use this reference when the user asks to create, inspect, modify, remove, or explain a Fusionclaw Data Extract, database extract, PL/SQL extract, REF CURSOR export, or an `ora_int_dbextract_*` capability.

## Architecture Boundary

A PL/SQL Data Extract is an Agentic App configuration feature. Its source of truth is `applicationMetadata.dataExtracts` in the `.app` file. The authoring layer derives a matching app-level capability whose id and name are `ora_int_dbextract_<normalized-extract-name>`.

This generated capability is a narrow exception to the normal rule that new capabilities are workflow-owned. Never hand-author it as a generic app capability and never replace it with a workflow `CAPABILITY` trigger.

The platform already owns the execution path:

`Data Extract capability -> container runtime -> private Orchestrator PL/SQL export service -> PACKAGE.PROCEDURE -> CSV in the active task workspace`

Do not create or request an External REST Tool, MCP tool, Business Object tool, custom REST resource, or workflow wrapper to publish the package procedure. The private platform endpoint is implementation infrastructure, not an application artifact.

The application-owned database dependency is the deployed PL/SQL package/procedure and the execution privilege needed by the platform database connection. If the user asks for end-to-end implementation and the PL/SQL source location is in scope, follow that repository's package/XDF conventions. If the owning module is unknown, ask only for the PL/SQL target module or path; do not ask for a REST endpoint.

## Supported Definition

The CLI currently authors only `type: "PLSQL"`. Preserve RODS or other provider entries already present, but do not claim their configuration is supported by these commands.

Each PL/SQL Data Extract requires:

- immutable `id`, generated by the CLI for a new definition;
- `name` and reusable functional `description`;
- unquoted `procedure` in `PACKAGE.PROCEDURE` form;
- `dataSetMode` of `single` or `multiple`;
- zero or more typed input parameters using only `STRING`, `NUMBER`, `BOOLEAN`, or `DATE`;
- for multiple mode, at least one unique non-empty data-set `code`.

All configured input values are currently required at invocation time. `DATE` inputs use `YYYY-MM-DD`. Do not add or rely on an optional `required` flag in parameter metadata.

For multiple mode, define the shared parameters once at the extract level. The CLI materializes those parameters into every serialized `dataSets[*].parameters` list because the runtime resolves inputs from the selected data set. Do not configure `P_EXTRACT_CODE`; it is reserved and injected by the platform as the first input for each selected data set.

## PL/SQL Procedure Contract

Inputs are bound positionally in the same order as the configured parameter list.

- Single mode: configured IN parameters, followed by the five OUT parameters below.
- Multiple mode: `P_EXTRACT_CODE IN VARCHAR2`, then configured IN parameters, followed by the five OUT parameters below.

The final five OUT parameters, in this exact order, are:

1. status `OUT VARCHAR2`; return `SUCCESS` for a successful export;
2. error code `OUT VARCHAR2`;
3. error message `OUT VARCHAR2`;
4. row count `OUT NUMBER`;
5. result set `OUT SYS_REFCURSOR`.

Names for the OUT parameters are conventional; their order and compatible types are the runtime contract. The reported row count must match the REF CURSOR row count.

## CLI Workflow

Use the dedicated commands instead of editing `.app` JSON directly:

- List: `aistudio list-data-extracts --file <app-file>`
- Inspect: `aistudio get-data-extract --file <app-file> --args '{"dataExtractId":"<id>"}'`
- Add: `aistudio do-add-data-extract --file <app-file> --args @<definition-file>`
- Modify: `aistudio do-modify-data-extract --file <app-file> --args @<patch-file>`
- Remove: `aistudio do-remove-data-extract --file <app-file> --args '{"dataExtractId":"<id>"}'`
- Validate: `aistudio validate-app --file <app-file>`

Run mutations serially. Use `--dry-run` only when the user explicitly requests an exact preview. A modify operation preserves the Data Extract id. Renaming changes the derived capability id, so the command removes the old generated capability and creates the new one atomically. Removal deletes only the capability derived from that Data Extract and preserves unrelated capabilities.

For a large definition, write the command arguments to an artifact-scoped scratch JSON file and pass it with `--args @<file>` rather than embedding deeply nested JSON in the shell.

Example single-mode definition:

```json
{
  "name": "Maintenance Export",
  "description": "Exports maintenance data for a selected organization.",
  "procedure": "FAI_MNT_EXPORT_PKG.EXPORT_MAINTENANCE_EXTRACT",
  "dataSetMode": "single",
  "parameters": [
    {
      "name": "P_ORGANIZATION_CODE",
      "dataType": "STRING",
      "description": "Maintenance organization code."
    }
  ]
}
```

For multiple mode, add `dataSets` entries containing `code`, optional `name`, and optional `description`. Do not put `parameters` inside command-level data-set entries; the CLI copies the shared parameter definitions into every serialized data set.

## Verification Boundary

`validate-app` proves local definition and generated-capability consistency. It cannot prove that the package is deployed, executable by the target environment, authorized for the current user, or returning a valid cursor. Confirm runtime success only from an invocation in the exact target environment that completes and produces the expected task-workspace CSV. Report local validation and live execution as separate evidence layers.
